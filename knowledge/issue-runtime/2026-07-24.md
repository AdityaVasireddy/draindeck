### CASE: adr22-repin-mount-path-string-mismatch
status: distilled
problem: ADR-22 re-pin verification script compared a bash hook's $(pwd)-sourced cwd string against Python's str(cwd) with strict equality and produced a false FAIL even though the synthetic hook fired correctly
decision: replaced the strict string-equality cwd check with a path-suffix comparison, re-ran the affected probe step fresh, and proposed (for a future pass) passing an explicit unique token as a hook argument instead of comparing paths at all
why: Git Bash on Windows mounts the Windows temp path as /tmp/... (MSYS translation) while Python sees the native C:\Users\... form — same directory, two different strings, so any strict comparison across that boundary is structurally wrong, not a probe-target defect
tags: [verification-harness, windows, git-bash, path-handling, adr-22]

#### JUDGMENT (distilled 2026-07-25)
Rejected alternative: treating the FAIL as a genuine mechanism failure and investigating the synthetic hook itself for a bug.
Tradeoff: treating it as a mechanism failure would have led to debugging the wrong component (the hook was firing correctly); recognizing it as a verification-script defect took a moment longer to diagnose but pointed the fix at the actual broken code.
Tipping factor: Git Bash mounts the Windows temp path as `/tmp/...` (MSYS translation) while Python sees the native `C:\Users\...` form — the same directory, two different strings — so any strict string-equality comparison across that boundary is structurally wrong regardless of whether the probed mechanism works.

### CASE: unbounded-find-root-kills-session
status: distilled
problem: a `find / -maxdepth 6 -ipath ...` issued from the Bash tool in this Windows/Git-Bash environment did not return in reasonable time and required a manual Ctrl+C that killed the entire Claude Code session, losing an in-flight background task
decision: going forward, scope every find to the narrowest known root (e.g. the specific scratch directory in question) and avoid `find /` entirely in this environment
why: a session-wide kill is a much larger cost than the mild inconvenience of an over-narrow search that has to be widened later
tags: [tooling-safety, find, windows, git-bash, session-crash]

#### JUDGMENT (distilled 2026-07-25)
Rejected alternative: continuing to use unscoped `find /` searches when double-checking for cross-contamination, treating the risk as acceptable given the thoroughness gained.
Tradeoff: an unscoped search can't miss anything outside the known scratch area, but on this Windows/Git-Bash environment it did not return in reasonable time and required a Ctrl+C that killed the entire session, losing an in-flight background task; scoping to the narrowest known root risks missing evidence outside that root but returns instantly and never risks the session.
Tipping factor: a session-wide kill is a much larger cost than the mild inconvenience of an over-narrow search that has to be widened later.

### CASE: settings-json-write-vs-edit-permission-mismatch
status: distilled
problem: four `Write(path)` deny rules in the user-scope `~/.claude/settings.json` (Write(**/.env*), Write(**/secrets/**), Write(**/.ssh/**), Write(.github/workflows/*)) are not matched by the CLI's file permission checks — only Edit(path) rules are — and this had been silently true since at least CLI 2.1.211 (transcript-confirmed 2026-07-16), a full week and several version bumps before it was noticed on 2026-07-24 at 2.1.215
decision: applied the straight Write( -> Edit( replacement diff to ~/.claude/settings.json, then ran the mechanical verification (one claude -p spawn, default --setting-sources, 8 attempts: Edit then Write against all 4 target files) — PASS: all 8 denied in-transcript (tool_result is_error:true, "File is in a directory that is denied by your permission settings"), all 4 files independently re-hashed byte-identical pre/post, claude_code_version=2.1.215 witnessed in the same transcript
why: the fix is not real until the rule is watched to actually deny, mechanically, not just re-worded — same discipline this project already applies to ADR-22's engine-level controls, now extended to user-scope CLI config
tags: [permission-rules, settings-json, silent-failure, cli-behavior, security]

#### JUDGMENT (distilled 2026-07-25)
Rejected alternative: applying the `Write(`→`Edit(` diff and trusting the CLI's own documentation ("Edit rules cover all file-editing tools") as sufficient confirmation the fix worked.
Tradeoff: trusting the documentation is faster and matches the CLI's stated behavior, but a fix trusted without independent verification would repeat the exact failure mode being fixed (a rule that looks correct but isn't actually enforced); running the 8-attempt mechanical test costs extra verification time but proves the fix on disk, not just in wording.
Tipping factor: this project already applies mechanical-verification discipline to ADR-22's engine-level controls, and the same standard was extended to user-scope CLI config rather than accepting a documentation claim at face value.
