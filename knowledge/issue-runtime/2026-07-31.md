## Cases

### CASE: sentinel-pause-after-stdin-delivery-not-before
status: cited
problem: the sentinel's pause point sat between writing the child's pidfile and calling communicate(), so a real claude -p child spawned with its prompt never delivered, hit its own 3s stdin grace period, and self-killed every time (confirmed via a real stderr.log showing "Input must be provided either through stdin...").
decision: split the single communicate() call into three explicit steps — off-thread stdin write, then the sentinel pause, then wait/timeout — so the pause always lands on a child that already has its prompt.
why: the pause's whole purpose is to freeze a live, working child for external inspection; pausing before the prompt is delivered freezes nothing meaningful and guarantees the child dies on its own before anyone can act.
tags: [sentinel, item-9, stdin, race-condition, claude-headless]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: leaving the pause point where it was (between pidfile write and `communicate()`), on the theory that "after the child is live" was already satisfied.
Tradeoff: leaving it there requires no rework, but the pause's whole purpose is to freeze a live, working child for external inspection — pausing before the prompt is delivered freezes nothing meaningful and guarantees the child dies on its own before anyone can act; splitting `communicate()` to deliver the prompt first costs restructuring the spawn/wait path but produces a pause that actually captures useful state.
Tipping factor: the pause's whole purpose is to freeze a live, working child for external inspection, and pausing before the prompt is delivered freezes nothing meaningful — confirmed directly via a real `stderr.log` showing the child self-killed on stdin starvation.

### CASE: stdin-write-off-thread-bounded-join-not-synchronous
status: cited
problem: the first draft of the split communicate() used a plain synchronous proc.stdin.write(prompt_bytes) before the pause, which would hang forever against a child that never reads stdin at all (the stdin PIPE has a small OS buffer).
decision: moved the stdin write onto a background thread with writer.join(timeout=cfg.timeout_seconds); a stalled write is treated as a timeout (kill+reap), same as before the split.
why: running the existing regression test tests/unit/test_engine.py::test_timeout_arms_when_child_never_reads_stdin against the naive synchronous draft would have hung it — the test exists specifically to pin that a large prompt against a non-reading child must not block the timeout from arming.
tags: [sentinel, threading, regression-test, claude-headless]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: a plain synchronous `proc.stdin.write(prompt_bytes)` before the pause.
Tradeoff: synchronous write is simpler code with no threading, but it would hang forever against a child that never reads stdin at all, since the stdin PIPE has a small OS buffer; writing on a bounded-join background thread costs more code but preserves the existing timeout-arms-regardless-of-stdin guarantee.
Tipping factor: running the existing regression test (`test_timeout_arms_when_child_never_reads_stdin`) against the naive synchronous draft would have hung it — the test exists specifically to pin that a large prompt against a non-reading child must not block the timeout from arming.

## Commands that worked
- `cmd.exe //c '<command>'` (doubled leading slash) — the reliable way to invoke any Windows command with single-slash flags (`taskkill /PID`, `tasklist /FI`, `python -m pytest ... /c` cases) from this environment's Git Bash without MSYS mangling the flag into a bogus path. Discovered after `cmd.exe /c '...'` (single slash) silently opened an interactive shell instead of running the command, and bare `taskkill /PID <n> /F` from Git Bash directly errored with `Invalid argument/option - 'C:/Program Files/Git/PID'`.
- `powershell.exe -NoProfile -Command 'Get-CimInstance Win32_Process | Where-Object { $_.ParentProcessId -eq <pid> } | ...'` — reliable way to get real parent-child process relationships on Windows; `tasklist` alone doesn't expose PPID. Must single-quote the whole `-Command` argument from Git Bash or `$_` gets expanded by bash itself before reaching PowerShell.
- Python's own permission-safe `shutil.rmtree` with an `onexc` handler that `os.chmod(path, 0o700)` before retrying — reliably clears a stale `%TEMP%\ch` durability-harness scratch dir full of git's own read-only `.git/objects/**` files; plain `shutil.rmtree`/`rm -rf`/naive PowerShell `Remove-Item -Force` all failed on this.
- `env -u ITEM9_SENTINEL -u ANTHROPIC_API_KEY .venv/Scripts/python.exe tests/crash/harness.py <dir> <seed>` — the durability harness invocation used for every Row F re-gate this session; 60/60 both seeds, three separate times across rebuilds.
