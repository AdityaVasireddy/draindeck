### CASE: restore-guard-must-not-supersede-inflight-halt
status: distilled
problem: A naive `finally: adapter.checkout_branch(...)` would, if the checkout itself raised, replace/mask any exception or exit code already in flight from the try/except above it (Python's finally-supersedes-return/exception semantics) — meaning a shutdown git failure could silently turn a real `OrchestratorHalt` into a confusing, unrelated git error instead.
decision: Wrapped the restore call in its own inner `except RepoError` inside the `finally` — logs a `[shutdown] WARNING` to stderr and does not re-raise — and proved this with a dedicated test (`test_restore_failure_does_not_supersede_inflight_halt`) that makes the checkout raise `RepoError` on the shutdown call specifically while `orch.run()` raises `OrchestratorHalt`, asserting `exit_code == 2` still comes back and both messages land on stderr.
why: The reviewer explicitly asked for "a test asserting the halt exit code survives a failing restore" as the artifact proving the guard, not an assertion about the code's shape — this is exactly the kind of self-supersession bug that would otherwise ship invisibly, since it only manifests when two failures coincide (a halt AND a bad shutdown checkout).
tags: [testing, finally-semantics, exception-handling, verification-discipline]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: a naive `finally: adapter.checkout_branch(...)` with no inner exception handling around the restore call.
Tradeoff: the naive form is simpler code, but Python's finally-supersedes-return/exception semantics mean a checkout failure during shutdown would silently mask or replace any exception or exit code already in flight (e.g. a real `OrchestratorHalt`), turning it into a confusing, unrelated git error instead; wrapping the restore in its own inner `except RepoError` costs more code but guarantees an in-flight halt's exit code survives a failing restore.
Tipping factor: the reviewer explicitly required a test asserting the halt exit code survives a failing restore, as the artifact proving the guard — this class of self-supersession bug only manifests when two failures coincide and would otherwise ship invisibly.

fault injection: kill `claude -p` mid-execution, resume, and prove from the event log and
git refs that recovery reaps the orphan without repeating or double-committing work. A

## Cases

### CASE: orphan-injection-requires-killing-the-orchestrator-not-the-child
status: cited
problem: The task was framed as "kill claude -p mid-execution," but it was unclear what process to actually kill to produce a real orphan for the reconciler to reap.
decision: Traced from source that `run()` is fully synchronous — `Popen` then `proc.communicate()` block in the same top-level orchestrator process — so killing only the `claude -p` child leaves the still-alive orchestrator to `communicate()` normally and clean up its own pidfile; a real orphan requires killing the orchestrator process itself while its child is alive. Verified empirically via `tasklist` in every injection run this session.
why: If only the child were killed, the orchestrator would observe the failed/killed exit code inside its own still-running process and unlink the pidfile normally, so recovery would never have anything to reap — the task's own framing was insufficient by construction.
tags: [fault-injection, process-architecture, orphan-recovery, windows]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: killing only the `claude -p` child process, per the task's original framing ("kill claude -p mid-execution").
Tradeoff: killing only the child matches the literal task framing and is simpler to script, but `run()` is fully synchronous — `Popen` then `communicate()` block in the same orchestrator process — so killing only the child leaves the still-alive orchestrator to observe the exit and clean up its own pidfile normally, meaning recovery would never have anything to reap; killing the orchestrator itself while its child is alive costs a different kill target than the task literally named but is the only way to produce a real orphan.
Tipping factor: tracing `run()`'s synchronous Popen-then-communicate() shape in source showed that killing only the child would let the orchestrator clean up normally, making the task's own framing insufficient by construction.

### CASE: taskkill-no-slash-t-confirmed-to-orphan-real-child-on-windows
status: distilled
problem: The kill mechanism's viability was unverified going in — this codebase has no Windows job-object/process-group binding in its `Popen` call (`popen_kwargs` is POSIX-only via `start_new_session=True`), so it was unknown whether `taskkill /PID <orchestrator_pid> /F` (without `/T`) would leave the real `claude -p` child alive or terminate it with its parent.
decision: Verified empirically via `tasklist /FI "PID eq <child_pid>"` immediately after `taskkill /PID <orch_pid> /F` (no `/T`) in every injection run (v1, v2, v3) — the child (`cmd.exe` wrapping `claude -p`) remained alive each time. The reviewer required this live-child witness as a mandatory pre-check (GAP-1) before any reap result could be trusted.
why: On POSIX, `start_new_session=True` already guarantees child survival by source inspection alone, but the Windows path has no equivalent in source, so it had to be established empirically; the reviewer's stated reasoning was that a reap of an already-dead child is indistinguishable in the event log from a reap of a genuine orphan — "the same failure class as the glob bug, one layer up."
tags: [windows, taskkill, fault-injection, verification, orphan-recovery]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: trusting that `taskkill /PID <pid> /F` (no `/T`) would leave the child alive, by analogy with the POSIX path's `start_new_session=True` guarantee, without empirically checking the Windows behavior.
Tradeoff: trusting the analogy would save an empirical check, but the codebase has no Windows job-object/process-group binding in its `Popen` call, so nothing in source actually guarantees child survival on Windows the way `start_new_session=True` does on POSIX; verifying empirically via `tasklist` immediately after each kill costs an extra witness step but confirms the mechanism actually works before trusting any reap result.
Tipping factor: the POSIX guarantee is visible in source, but the Windows path has no equivalent, so it had to be established empirically — a reap of an already-dead child is indistinguishable in the event log from a reap of a genuine orphan.

### CASE: kill-window-aborts-if-child-already-finished
status: distilled
problem: The ~15-20s post-pidfile kill-delay calibration rested on only 5 samples from an earlier session; if the killed child's issue finished faster than that window (cold cache, trivial issue), the kill would land after the work was already committed, silently testing nothing while still reporting a "pass."
decision: Extended the pre-kill re-check to abort the kill entirely (do not call `taskkill`) if `CommitCreated` or `ExecutionFinished` had already appeared for that execution_id at the kill decision point — mark the attempt "child completed before kill window" and retry on the next issue rather than scoring a post-finish kill as a valid recovery test.
why: The reviewer required this explicitly because a kill landing after the work already finished would produce a false-positive "recovery worked" result with nothing actually exercised.
tags: [fault-injection, methodology, calibration, false-positive]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: keeping the original fixed ~15-20s kill-delay calibration and firing the kill unconditionally at that point regardless of the execution's actual progress.
Tradeoff: a fixed delay is simpler to implement and needs no extra state check, but the calibration rested on only 5 samples from an earlier session, and if a killed issue finished faster than the window, the kill would land after the work was already committed, silently testing nothing while still reporting a pass; checking for `CommitCreated`/`ExecutionFinished` before firing and aborting if already present costs an extra check but prevents a false-positive result.
Tipping factor: the reviewer required this because a kill landing after the work already finished would produce a false-positive "recovery worked" result with nothing actually exercised — indistinguishable from a real successful test without the check.
