## Cases

### CASE: durability-fixture-f4-stale-not-regression
status: auto
problem: durability harness fails identically at fixture f4 on both seed 42 and seed 1337 (55/60 passed), AssertionError "reap_orphans did not report 042-e1: []"
decision: diagnosed as a stale test fixture, not a production regression — `run_engine_orphan_fixture` registers the orphan via `engine._write_pidfile()` alone (always writes `version:2, state:"resolving"`, no `worker`/`ancestry`) and never calls `_resolve_and_persist_worker`, so `reap_orphans()`'s empty return is correct under current policy
why: hand-traced `_worker_liveness` against the fixture's actual record — `state != "resolved"` returns `"unknown"` before reaching the alive/dead branches, and `"unknown"` records are intentionally retained rather than reaped, exactly matching the observed empty `repairs` list
tags: [durability, harness, crash-recovery, liveness, diagnosis]
until: Adi picks Option A (patch the fixture to drive the real `_write_pidfile → _resolve_and_persist_worker` path) or Option B (treat the stuck-"resolving" orphan window as a real src/ defect) and the harness shows 60/60 on both seeds

### CASE: reap-stuck-resolving-via-shim-timeout
status: auto
problem: v2 pidfile records left in `state:"resolving"` past a crash (before `_resolve_and_persist_worker` ever runs) were retained indefinitely by `_worker_liveness`'s "unknown" verdict, so a genuinely dead orphan in that window was never reaped
decision: added a `resolving`-state branch to `_worker_liveness` classifying via `started_at` age against a timeout — fresh→`"unknown"` (retained), timed-out+shim-alive→`"alive"`, timed-out+shim-dead→`"dead"` (reaped), timed-out+shim-unresolvable/malformed→`"unknown"`
why: `started_at` is the only timing field written unconditionally by `_write_pidfile` for every v2 record regardless of state, so it was the only available signal without adding a new field; the reap rule had to distinguish "still legitimately mid-resolve" from "crashed before resolving finished"
tags: [durability, recovery, orphan-reaping, liveness, worker-resolution]

### CASE: windows-resolving-timeout-tied-to-cfg-not-resolve-loop
status: auto
problem: choosing a stale-timeout bound for the new `resolving`-state reap branch risked using the POSIX resolve-loop constant (`_LEAF_MAX_SECONDS = 10.0`) as the threshold
decision: tied the timeout to `cfg.timeout_seconds + cfg.containment_confirmation_seconds + margin` instead, not the short resolve-loop constant
why: `_resolve_and_persist_worker` (which promotes `resolving`→`resolved`) only runs on the POSIX path — the Windows path (`_run_windows_contained`) writes the pidfile once and never promotes it, staying `"resolving"` for the entire legitimate run by design (Job-object containment tracks membership directly). A short resolve-loop-tuned timeout would have made every in-flight Windows execution falsely "reapable" long before it finished.
tags: [durability, windows, containment, timeout, cross-platform]

### CASE: stale-after-seconds-threaded-param-not-fixture-backdate
status: auto
problem: the harness needed a way to make f4's fresh `resolving` record appear stale without waiting out the real cfg-derived timeout
decision: threaded `stale_after_seconds: Optional[float] = None` as an explicit kwarg on `reap_orphans` and `is_execution_alive` (default `None` → cfg-derived) rather than having the harness hand-construct a backdated `started_at` in the fixture JSON
why: backdating the fixture's JSON directly would duplicate `_write_identity_record`'s format outside the real production write path — exactly the kind of fixture drift that produced the original f4 gap (the fixture calling `_write_pidfile` alone, one production step short of reality); threading the param keeps the harness on the real write path and only substitutes the threshold
tags: [durability, harness, testing, fixture-design]

### CASE: f4-adversarial-retain-guard-extends-existing-fixture
status: auto
problem: the 0.0-threshold reap injection alone could not prove the timeout comparison direction (an inverted comparison would also "pass" a same-side test)
decision: added an adversarial assertion — call `reap_orphans(stale_after_seconds=9999)` first, assert the fresh record is NOT reaped, its pidfile still exists, and the dummy process is still alive — as an extension of f4's existing record/process rather than a new fixture
why: f4 already constructs the exact artifact needed (a real v2 `resolving` record backed by a genuinely running child); reusing it proves the comparison direction on identical data instead of a second synthetic record that could accidentally exercise a different code path, and avoids spawning a second 300s child for no added rigor
tags: [durability, harness, testing, adversarial-assertion]
