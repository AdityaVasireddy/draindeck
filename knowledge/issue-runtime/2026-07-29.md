### CASE: parent-only-kill-no-t-flag-for-orphan-harness
status: cited
problem: the item-9 crash harness needed a kill method that leaves the `claude -p` child running as a real orphan for the reconciler to reap, without accidentally producing a self-dead child that would mimic the same reconciler outcome.
decision: fixed the kill method across every crash row to `taskkill /PID <orchestrator-pid> /F` with no `/T`, reserving exactly one isolated `/T` kill inside a dedicated discriminator self-test.
why: `loop.py:212`'s `engine.run()` runs synchronously inside the orchestrator process, so killing only the orchestrator leaves the child running as a genuine orphan; `/T` tree-kills the child too and collapses the exact state Row D exists to witness.
tags: [crash-harness, item-9, taskkill, design]

#### JUDGMENT (distilled 2026-07-31)
Rejected alternative: using `taskkill /T` (tree-kill) as the harness's standard kill method across all crash rows.
Tradeoff: `/T` is the more commonly reached-for kill flag and guarantees clean process-tree teardown, but it tree-kills the child along with the orchestrator, collapsing the exact live-orphan state Row D exists to witness; parent-only kill (no `/T`) as the default costs a messier teardown (child left running) but preserves the real orphan scenario the harness needs to test.
Tipping factor: `loop.py:212`'s `engine.run()` runs synchronously inside the orchestrator process, so killing only the orchestrator leaves the child running as a genuine orphan — `/T` would defeat that by tree-killing the child too.
