### CASE: encoding-verification-via-dotnet-not-powershell-pipe
status: cited
problem: Needed the true on-disk byte sequence of a placeholder dash character in config.example.yaml before editing, but `Get-Content -Encoding UTF8` piped into `Format-Hex` produced a `3F` byte that looked like data loss.
decision: Read raw file bytes directly via `[System.IO.File]::ReadAllBytes` + `Encoding.UTF8.GetString/GetBytes` instead of piping `Get-Content` output into `Format-Hex`, confirming the true byte sequence was `E2 80 94` (em dash), not `3F`.
why: `Format-Hex` operating on an already-decoded .NET string re-encodes it with its own default codec for display, substituting undisplayable characters — it does not reflect the file's actual on-disk bytes, so hex-dumping a decoded string pipeline is unreliable for verifying true byte content.
tags: [powershell, encoding, dotnet, verification]

#### JUDGMENT (distilled 2026-08-09)
Rejected alternative: trusting `Get-Content -Encoding UTF8 | Format-Hex` output as the true on-disk byte sequence.
Tradeoff: piping through `Format-Hex` is the more familiar one-liner, but it operates on an already-decoded .NET string and re-encodes it with its own default codec for display, not reflecting real on-disk bytes; reading raw bytes via `.NET ReadAllBytes` costs an extra manual step but reflects the file's true content.
Tipping factor: `Format-Hex` on a decoded string doesn't reflect the file's actual on-disk bytes, confirmed by the discrepancy between the reported `3F` byte and the actual `E2 80 94` em dash.

status: distilled
problem: A `$env:TEMP`-based `Test-Path` check for stale harness temp dirs returned corrupted/empty output because the Bash tool's own shell tried to expand `$env` as if it were a bash variable, leaving a mangled `:TEMP` fragment before PowerShell ever saw the line.
decision: Recognized the corrupted output as a shell-passthrough artifact rather than a real PowerShell/filesystem result, and re-ran the same check with quoting adjusted so `$env:TEMP` reached PowerShell intact.

tags: [powershell, bash-tool, quoting, env-vars]

#### JUDGMENT (distilled 2026-08-09)
Rejected alternative: trusting the corrupted/empty `$env:TEMP`-based check result as a real filesystem finding.
Tradeoff: trusting the corrupted output at face value would be faster, but it would have been silently wrong — the Bash tool's own shell pre-expanded `$env` before PowerShell ever saw the line; recognizing it as a shell-passthrough artifact and re-running with adjusted quoting costs an extra diagnostic step but produces a correct result.
Tipping factor: the Bash tool's outer shell interprets `$`-prefixed tokens before handing the command to `powershell.exe`, so PowerShell variable syntax beginning with `$` is at risk of pre-expansion/corruption unless quoted to survive the outer shell first.
