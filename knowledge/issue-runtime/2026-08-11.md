### CASE: windows-temp-dir-collision-crash-harness
status: cited
problem: re-running the durability crash harness against the same `%TEMP%\ch` root intermittently failed with a Windows deferred-deletion race — git marks object files read-only, and the previous run's `rmtree` hadn't fully released file handles before the directory was recreated.
decision: use fresh, uniquely-named temp roots per seed/run (e.g. `ch42v`, `ch1337v`) instead of reusing `%TEMP%\ch`; the harness code itself was left untouched.
why: diagnosed as an OS-level file-handle race specific to this environment, not a regression from the code change under test.
tags: [windows, crash-harness, testing, flaky]

#### JUDGMENT (distilled 2026-08-12)
Rejected alternative: modify the harness code (e.g. add retry/cleanup logic) to make repeated same-root runs reliable.
Tradeoff: fixing the harness would make reused temp roots reliable going forward, but requires touching tested harness code for what was diagnosed as an environment-level race rather than a code defect; picking fresh roots costs nothing in the harness but leaves the underlying stale-root race unfixed for future reuse.
Tipping factor: the race was diagnosed as an OS-level file-handle issue specific to this environment, not a regression from the code under test, so avoiding it didn't require touching the harness.
