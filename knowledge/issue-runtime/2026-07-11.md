## Cases

### CASE: merge-in-object-database-not-worktree
status: distilled
problem: the CommitIntent→CommitCreated merge needed a git-level design letting the reconciler determine, after a crash, whether the merge completed, without risking a corrupted worktree.
decision: `merge_to` performs the entire merge in the object database (`merge-tree` → `commit-tree` → atomic `update-ref`) instead of touching the worktree.
why: reduces post-crash states to exactly two ("ref moved or not"), distinguishable via `is_ancestor` — matching doc 02 §4.2's witness — and guarantees a crashed merge can never dirty the worktree.
tags: [git, durability, repository-adapter, crash-recovery]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: perform the merge via normal worktree operations (checkout, merge, commit in the working tree).
Tradeoff: a worktree merge is the conventional git workflow and needs no object-database plumbing, but leaves ambiguous post-crash states (partial merge, dirty worktree) that require more complex reconciliation.
Tipping factor: an object-database-only merge reduces post-crash states to exactly two, distinguishable via `is_ancestor` — which satisfies doc 02 §4.2's witness definition by construction, while a worktree merge would not.

### CASE: tamper-detection-raises-not-forges
status: cited
problem: the check-2 seam (`check_unwitnessed_commit`) can encounter a world that was rewritten under the reconciler, where the expected `merge_commit` no longer matches.
decision: raise `ReconcilerTamperError` instead of forging a synthetic `merge_commit` event.
why: ADR-11 join-key integrity requires refusing to fabricate provenance when the underlying git state has been tampered with.
tags: [reconciler, integrity, adr-11, error-handling]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: forge a synthetic `merge_commit` event when the expected commit doesn't match, so reconciliation can proceed autonomously without operator intervention.
Tradeoff: forging keeps the system unblocked but silently fabricates provenance; raising halts progress but preserves integrity.
Tipping factor: ADR-11 join-key integrity is a frozen requirement that explicitly forbids fabricating provenance, making this a contract compliance question rather than a case-by-case tradeoff judgment.

### CASE: m2-mutation-caught-by-unit-test-not-harness
status: distilled
problem: mutation M2 (dropping `clean -fd` from `reset_hard`) was expected, per the plan, to be caught by the crash harness, but verification showed it was caught by the adapter unit test instead.
decision: accept the adapter unit test as the enforcement point for this invariant rather than adding a dedicated harness scenario.
why: the check-3/residue paths snapshot untracked files before any reset — that snapshot behavior is what pins `clean -fd`, and it lives at the adapter primitive level where the unit test exercises it directly; the harness only observes it indirectly.
tags: [testing, mutation-testing, crash-harness, repository-adapter]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: add a dedicated crash-harness scenario to catch mutation M2, as the original plan called for.
Tradeoff: a harness scenario tests the invariant end-to-end through crash recovery, but the harness only observes clean -fd's effect indirectly; the unit test exercises the adapter primitive directly, at the exact level where the snapshot-before-reset behavior lives.
Tipping factor: verification showed the mutation was already caught by the adapter unit test — the enforcement point was found empirically, not chosen a priori, so adding a redundant harness scenario would duplicate coverage without adding value.

### CASE: base-commit-carried-on-view
status: distilled
problem: the `preserve_residue` seam receives only the `ExecutionView`, but needs the issue's `base_commit` to do its work.
decision: carry `base_commit` onto the view at spawn time rather than passing it as a separate parameter to the seam.
why: keeps the seam self-contained on a single argument instead of coupling its signature to extra spawn-time context.
tags: [reconciler, projection, seam-design]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: pass `base_commit` as a separate parameter to the `preserve_residue` seam alongside the `ExecutionView`.
Tradeoff: a separate parameter leaves the view's schema untouched but couples the seam's signature to extra spawn-time context that every caller must thread through; carrying it on the view keeps the seam single-argument at the cost of enlarging the view.
Tipping factor: seam-signature simplicity was weighted over minimizing the view's surface area, since the view already represents spawn-time state and `base_commit` is legitimately part of that provenance.
