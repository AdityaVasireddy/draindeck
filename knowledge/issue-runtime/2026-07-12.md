## Cases

### CASE: stdin-write-then-wait-timeout-hole
status: distilled
problem: the initial plan wrote the prompt to the child's stdin, then enforced the wall-clock timeout via a separate `proc.wait(timeout=...)` call; if the child dies early, wedges before reading stdin, or the prompt exceeds the pipe buffer while the child isn't draining, the parent blocks forever inside the stdin write, which is reached before `proc.wait()` — so the timeout never arms.
decision: use `proc.communicate(input=prompt_bytes, timeout=cfg.timeout_seconds)` so the stdin write, wait, and timeout are one covered operation, with a unit test asserting a child that never reads stdin still returns `timed_out=True` within budget.
why: doc 02's "hard wall-clock timeout" guarantee has a hole if the write and the wait are separate blocking calls; combining them is the only way the timeout actually covers the write.
tags: [subprocess, timeout, concurrency, engine]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: keep the original design — write the prompt to stdin, then enforce the timeout via a separate `proc.wait(timeout=...)` call.
Tradeoff: the separate-call design maps directly onto "write then wait" intuition and needed no restructuring, but leaves a real blocking window (stdin write reached before `proc.wait()`) that defeats the documented timeout guarantee.
Tipping factor: the specific failure mode (child dies early / wedges before reading stdin / prompt exceeds the pipe buffer) directly defeats doc 02's hard wall-clock guarantee, and folding stdin-write + wait + timeout into one covered `proc.communicate()` call is the only way to close that hole without inventing a separate watchdog thread.

### CASE: billing-guard-raise-not-assert
status: cited

why: assert statements disappear under `python -O`, and this is a billing invariant (subscription vs. API billing per ADR-18) that must hold on every spawn regardless of interpreter flags.
tags: [adr-18, billing, python-gotcha, error-handling]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: leave the check as `assert "ANTHROPIC_API_KEY" not in env`.
Tradeoff: assert reads as the terser, more idiomatic invariant-check already used elsewhere in the codebase, but silently disappears under `python -O`.
Tipping factor: this specific check guards a billing invariant that must hold unconditionally on every spawn (subscription vs. API billing per ADR-18), so the interpreter-flag fragility of assert is unacceptable no matter how idiomatic it looks.

### CASE: pid-in-log-is-writer-not-engine-child
status: distilled
problem: needed to determine whose pid `ExecutionSpawned`/`ExecutionFinished` should record — the orchestrator/writer process, or the spawned `claude -p` child — since the engine wrapper design keeps the child pid out of the event log entirely (pidfile-only).

why: a child pid would differ between spawn and finish even without a crash, so if I-h meant the child pid the interface would need to change; verifying against the actual harness/worker code settled which reading of doc 03 is correct before writing dependent code.
tags: [doc-03, pid-semantics, crash-harness, verification]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: assume doc 03's pid field means the engine child pid (as first raised — "if doc 03 means the engine child pid, this interface cannot satisfy I-h and the interface must change") and redesign `ClaudeHeadlessEngine`/`EngineResult` to surface the child pid into the event log.

### CASE: pidfile-only-no-in-memory-registry
status: distilled
problem: initial design included an in-memory process registry alongside the pidfile for tracking live engine children.
decision: drop the in-memory registry; `is_execution_alive` reads only the pidfile.
why: `is_execution_alive` is called by the reconciler in a fresh post-crash process where an in-memory dict would already be empty, and `run()` is synchronous with startup-only recovery, so there is never an in-process concurrent query — making the pidfile the only cross-crash-correct source and the registry pure redundancy.
tags: [engine, crash-recovery, simplification]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: keep an in-memory process registry alongside the pidfile, as originally designed.
Tradeoff: an in-memory registry could offer a faster, no-syscall liveness check within a single run, but adds a second source of truth that can't be trusted after a crash.
Tipping factor: `is_execution_alive` is called by the reconciler in a fresh post-crash process, where any in-memory registry would already be empty by construction — combined with `run()` being synchronous with startup-only recovery (no in-process concurrent query ever occurs), the registry had no scenario where it added correctness or performance.

### CASE: image-name-pinned-at-spawn-for-liveness-check
status: distilled
problem: `is_execution_alive`'s "matches an engine process" check had no defined image name; a hardcoded name (e.g. `claude.exe`) either breaks unit tests (which spawn a Python dummy) or checks nothing meaningful on Windows where the real child may be `node.exe`/`claude.exe` depending on install.
decision: record the resolved image name of the spawned process in the pidfile at spawn time and compare against that recorded value at check time.
why: this also strengthens the pid-reuse defense (a stale pidfile pointing at a reused pid of a different process would fail the image-name comparison), while staying test-agnostic since the dummy's own image name is what gets recorded and checked.
tags: [engine, pid-reuse, cross-platform, windows]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: hardcode an expected process image name (e.g., `claude.exe`) for the liveness check.
Tradeoff: a hardcoded name is simpler to write, but breaks unit tests (which spawn a Python dummy child, not `claude.exe`) or, if loosened, ends up checking nothing meaningful — and doesn't defend against pid reuse.
Tipping factor: recording the actual resolved image name at spawn time and comparing against it at check time is the only approach that stays correct across both the test double and the real Windows binary, while also strengthening the pid-reuse defense as a side effect.

Also noted (not drafted): the f4 planted-fixture design choice (reusing the harness's existing "planted state a timed kill can't produce" idiom instead of invasive worker.py surgery) — reasoning is largely reconstructible from the harness's own docstring, so it fails G3.

### CASE: allowedtools-falsified-denylist-is-the-real-fence
status: distilled
problem: the approved Session 5 plan fenced the engine subprocess with `--allowedTools` (doc 02 §3's "no network push, no credential access" requirement), but a live probe against `claude -p` 2.1.207 showed a non-listed tool (Bash under `--allowedTools Read`) and a non-matching Bash pattern (`whoami` under `Bash(echo:*)`) both ran freely, with `permission_denials` empty, under both `acceptEdits` and `default` permission modes — and the operator's ambient settings had no `allow` list at all, ruling out settings contamination as the cause.
decision: abandon `--allowedTools` as a security fence entirely; rebuild the engine fence around `--disallowedTools`, which live probes confirmed does hard-block matching tools/patterns and is chaining-resistant. Recorded as ADR-21 in doc 08 (doc 05 is frozen).
why: in `claude -p` non-interactive mode, a tool call matching neither an allow nor a deny rule defaults to running, not being denied — `--allowedTools` is additive auto-approve only, never restrictive, in any permission mode tested; the denylist was the only mechanism the probe showed actually enforcing.
tags: [adr-21, security, claude-cli, fencing, permissions]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: continue with the approved plan's `--allowedTools`-based fence, possibly after finding a permission-mode tweak that would make it restrictive.
Tradeoff: sticking with `--allowedTools` would have required no plan rebuild, but the probe showed it does not restrict anything under either permission mode tested (`acceptEdits` or `default`) — continuing with it would ship a fence that doesn't fence.
Tipping factor: three separate live probes converged on the same mechanism (a non-listed tool ran; a non-matching pattern ran; the "ambient settings contamination" hypothesis was ruled out by reading the actual settings file, which had no `allow` list at all) — this is empirical falsification of the plan's core mechanism, not a preference between two working designs.

### CASE: fence-block-signal-is-tool-result-error-not-permission-denials
status: distilled
problem: needed to know what observable signal marks a blocked tool call, for both the engine's own logic and future monitoring/detection.
decision: key detection on the `tool_result` entry's `is_error:true` ("not enabled in this context"), not on the `permission_denials` array — that array is empty for whole-tool `--disallowedTools` removal even though the block is real; it only populates for settings/pattern-level `deny` rules.
why: verified directly in the probe — a `--disallowedTools Bash` run hard-blocked the tool (tool_result error) with `permission_denials:[]`, while a `Bash(git push *)` ambient deny populated `permission_denials`; treating only `permission_denials` as the signal would silently miss whole-tool blocks.
tags: [adr-21, observability, claude-cli, detection]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: key detection/observability purely on the `permission_denials` array, the more discoverable and already-named field.
Tradeoff: `permission_denials` is simpler to check and was the assumed signal going in, but it stays empty for whole-tool `--disallowedTools` removal even though the block is real, so relying on it alone silently misses that class of enforced block.
Tipping factor: directly observing both block types in the probe (`--disallowedTools Bash` → empty `permission_denials` but a real `tool_result` error; ambient `Bash(git push *)` deny → populated `permission_denials`) showed the two signals are not interchangeable, forcing detection logic to check both.

### CASE: engine-fence-blocks-all-git-not-just-push
status: distilled

why: ADR-07 requires the engine never touch git at all — the orchestrator owns all git contact — so scoping the fence to the architectural boundary (all git) rather than to a specific observed risk (push) is what the existing invariant actually demands.
tags: [adr-21, adr-07, git, fencing]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: mirror the ambient settings' narrower scope and fence only `Bash(git push *)`.
Tradeoff: matching the ambient rule's scope is minimal and sufficient for the one risk that rule was written for (accidental pushes), but leaves other git subcommands (fetch, checkout, commit, etc.) reachable from inside the engine.
Tipping factor: ADR-07 ("the engine never touches git; the orchestrator owns all git contact") is an architectural boundary broader than "don't push" — the fence needed to match the invariant the architecture actually requires, not the narrower risk the ambient rule happened to cover.

### CASE: active-no-execution-healed-by-state-guard-not-emission-restructure
status: distilled
problem: after `IssueActivated` is durable but `ExecutionSpawned` is not (a crash window), a restart needs to correctly resume an ACTIVE issue with zero executions without re-running `IssueActivated` or losing the pinned `base_commit`.

why: `IssueActivated` only ever fires once per PENDING issue (doc 03 §1's PENDING→ACTIVE row is "Yes (replay)"-safe only because it doesn't re-run), so keeping the guard purely in the routing logic preserves the pinned `base_commit` without touching the emission contract.
tags: [reconciler, crash-recovery, doc-03, state-machine]

#### JUDGMENT (distilled 2026-07-12)
Rejected alternative: restructure event emission (change what `IssueActivated`/`ExecutionSpawned` record or when they fire) to close the ACTIVE-with-zero-executions crash window.
Tradeoff: restructuring emission could narrow the crash window by construction, but touches the frozen doc 03 §5 transition/emission contract; a routing guard changes only how `step()` dispatches, leaving the emission contract untouched.
Tipping factor: doc 03 §1's PENDING→ACTIVE row is already documented as "Yes (replay)"-safe specifically because `IssueActivated` never re-runs — a state-based guard in `step()` is sufficient to exploit that existing replay-safety guarantee, so no emission change was needed at all.
